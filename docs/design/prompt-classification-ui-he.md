# דיזיין: סיווג פרומפטים בדיעבד מתוך VS Code

תאריך: 31.10.2026
בסיס: `research/prompt-logging`, קוד `fbdcc68`
סטטוס: מומש מקומית ונבדק אוטומטית. [מדריך, תוצאות וצילומים](../concepts/prompt-classification-ui.md). קבלה ידנית בתוך VS Code ב־Windows עדיין פתוחה, לצד בדיקות פיצ׳רים 1–2.

## מטרה וגבולות

לאפשר למשתמש לעבור על הפרומפטים שנאספו במחקר, לציין מה סוג כל פרומפט ומה היו הסיבות או המטרות שלו, ולתקן סיווגים בהמשך. אין צורך לכתוב JSON, להפסיק שיחה או לענות על חלונית אחרי כל הודעה. אפשר לסווג בזמן העבודה או אחרי סיום המחקר.

הסיווג מתאר כוונה או סיבה שהמשתמש מדווח עליה. הוא אינו מוכיח שההתערבות שיפרה את המצגת. הפיצ׳ר אינו מפעיל מסווג LLM, אינו מנתח איכות ואינו קובע checkpoints. הצעות קיימות של מודל ניתנות להצגה ולאישור; יצירת הצעות אוטומטית היא פיצ׳ר 8.

לדוגמה: המשתמש מסיים עבודה על ״וקטורים — ניסיון 1״, פותח את מסך הסיווג, קורא פרומפט כמו ״הדוגמה הזו לא מסבירה למה צריך נרמול״, ובוחר ״תיקון או שינוי מכוון״ עם הסיבה ״הסבר לא ברור״. בהמשך הוא יכול לשנות או להוסיף סיבה; ההחלטה הקודמת נשארת בהיסטוריה.

## הבסיס הקיים והפערים

| קיים בקוד | מה נוסף בפיצ׳ר |
| --- | --- |
| `PROMPT_TYPES`, `REASONS`, `STAGES` | תוויות והסברים בממשק; אותה טקסונומיה התחלתית |
| `ResearchLog.classify` | שירות משותף עם שמירה מבוקרת, זיהוי התנגשויות וניסיונות חוזרים |
| `classification.suggested` ו־`classification.confirmed` | תצוגה נפרדת וחישוב ברור של הסיווג האנושי התקף |
| אירוע חדש לכל קריאת classify | היסטוריה ניתנת להצגה, ודילוג/ניקוי מפורשים |
| מזהי מחקר, פרומפט ואירוע | שיוך קבוע של העורך למחקר ולפרומפט הנבחרים |
| ייצוא JSONL | ייצוא האירועים החדשים ושחזור הסיווג התקף מההיסטוריה |

בנקודת הבסיס של הדיזיין לא היה query של תור פרומפטים, מסך סיווג, הגנת גרסה או משמעות נפרדת לדילוג. גם מקור/גרסת המסווג אינם שדות מפורשים בממשק classify הקיים. היכולות האלה מומשו כעת בשירות ובפאנל המתוארים להלן.

## מה מסווגים

יחידת הסיווג היא אירוע `prompt.recorded` שנאסף בפועל. הסיווג נשאר מחובר ל־`project_id`, ל־`session_id` ול־`prompt_id` המקוריים, ולא למיקומו של הפרומפט ברשימה או לחלון הפעיל.

כל סוג פרומפט יכול להופיע בתור: פתיחה, המשך רגיל, בקשת שינוי והודעה שאינה רלוונטית לניסוי. הודעת מודל אינה פרומפט אנושי לסיווג. לא יוצרים יחידות מלאכותיות עבור הודעות שלא נקלטו, ולא מפצלים פרומפט אחד למספר אירועים כדי לפשט את התיוג.

הודעה עם כמה כוונות מקבלת סוג ראשי אחד וסיבות מרובות. למשל, ״תמשיך, אבל קודם תתקן את הנוסחה ותגדיל את הטקסט״ יכולה לקבל סוג corrective ושתי סיבות. המשתמש בוחר; לא מסיקים סוג לפי מילות מפתח או מיקום בשיחה.

### סוג פרומפט — בחירה יחידה

| קוד קיים | תווית מוצעת | משמעות |
| --- | --- | --- |
| `initial` | פתיחת משימה | בקשת ההתחלה או הגדרת המשימה |
| `continuation` | המשך רגיל | בקשת המשך שאינה מבקשת תיקון או שינוי מכוון |
| `corrective` | תיקון או שינוי מכוון | שינוי בתוכן, בהצגה, בכוונה או בפתרון תקלה; אינו בהכרח תיקון של טעות |
| `irrelevant` | לא רלוונטי לניסוי | תוכן שנאסף אך אינו חלק מהתהליך המחקרי הנבדק |

אין ברירת מחדל אוטומטית ל־initial בפרומפט הראשון או ל־continuation בפרומפטים האחרים. אם המשתמש אינו יודע, הוא יכול לדלג; לא מוסיפים לו תווית של ודאות שלא דיווח עליה.

### סיבות או מטרות — בחירה מרובה ואופציונלית

| קוד קיים | תווית מוצעת |
| --- | --- |
| `factual_math` | דיוק עובדתי או מתמטי |
| `narrative_order` | רצף ההסבר או סדר ההצגה |
| `unclear_explanation` | הסבר לא ברור |
| `add_content` | הוספת תוכן |
| `remove_content` | הסרת תוכן |
| `visual_animation` | שינוי חזותי או אנימציה |
| `intent_mismatch` | אי־התאמה לכוונה |
| `technical_render` | בעיה טכנית או רינדור |
| `other` | אחר, עם פירוט קצר |

אין חובה לספק סיבה לכל פרומפט, ואין איסור טכני לציין סיבות לסוגים אחרים מלבד corrective. המשתמש מדווח על המטרה שלו; הסוג והסיבות הם ממדים נפרדים. בגרסה זו אין הערה חופשית נוספת מעבר לפירוט ״אחר״.

נשמרת ההבחנה הקיימת בין `reasons=null` — לא סופקו סיבות — לבין `reasons=[]` — נבדק והמשתמש בחר להשאיר ללא סיבות. בטופס חדש הסיבות מתחילות כלא־מסופקות. שינוי בחירות או לחיצה על ״ללא סיבות״ הופכים אותן לרשימה מפורשת, גם אם ריקה. עבור סיווג חדש עם other נדרש טקסט שאינו ריק; סיווגים ישנים עם other ללא פירוט נשארים קריאים ומוצגים ככאלה.

הקודים יישמרו עם `taxonomy_version=1`, בנפרד מגרסת סכמת SQLite. שינוי תרגום של תווית לא משנה את הקוד. שינוי משמעות או הוספת קטגוריות מחייבים גרסת טקסונומיה מתועדת; אין שכתוב של נתונים קודמים.

## חוויית המשתמש

פקודה **Research: Classify Prompts** פותחת פאנל עבור המחקר הנבחר. אפשר לבחור גם מחקר מושהה או שהסתיים, וגם סשן legacy שכבר מכיל פרומפטים. אין צורך לחבר מקור חדש, לחדש את המחקר או להפעיל שוב את איסוף השיחה כדי לסווג היסטוריה קיימת.

הפאנל כולל רשימת פרומפטים ועורך לפרומפט הנבחר. לכל שורה: מספר לצורכי ניווט, תמצית, מצב סיווג, האם קיימת הצעת מודל וזמן התצפית. המזהים נשמרים ברקע; המספר ברשימה אינו מזהה עמיד.

מסננים: ״טרם סווגו״ כברירת מחדל, ״דולגו״, ״סווגו״ ו־״הכול״. מופיעים מונים נפרדים לסך הפרומפטים שנאספו, סיווגים אנושיים תקפים, פרומפטים ללא סיווג ודילוגים. דילוגים הם תת־קבוצה של פרומפטים ללא סיווג ולא נספרים פעמיים בסיכום.

העורך מציג:

1. את הפרומפט המלא, ללא שינוי בתוכן המקור.
2. הקשר מצומצם שניתן להרחיב: תגובת המודל שקדמה לו, תשובות/פעולות המקושרות אליו והודעות שכנות. קשר עמום באמצעות `related_prompt_ids` מסומן כמשותף, ולא מוצג כקשר סיבתי מוכח לפרומפט הזה.
3. סוג אחד, כמה סיבות ופירוט other אם נבחר.
4. הצעת מודל באזור נפרד, אם קיימת, עם מקור וגרסה זמינים.
5. כפתורים: ״שמור״, ״שמור והבא״, ״דלג בינתיים״ לפרומפט ללא סיווג, ״הבא״ ו־״היסטוריה״. עבור סיווג קיים מופיעה גם ״נקה סיווג״.

אין popup על כל פרומפט ואין אישור לפני שליחת הודעה ב־Codex. שליחת פרומפטים והפעלת כלים אינן ממתינות לסיווג. קיצורי מקלדת, אם יתווספו, פועלים רק כשהפאנל ממוקד ואינם משתלטים על Enter בצ׳אט או בעורך הקוד.

כשהשיחה ממשיכה בזמן שהפאנל פתוח, נוספים פרומפטים לרשימה ברענון, בלי לשנות את הבחירה או את הטיוטה. הפאנל נשאר מוצמד למחקר שפתח אותו. החלפת המחקר בשורת המצב אינה מעבירה טיוטה למחקר אחר; מעבר מפורש בפאנל מציע שמירה, שמירת טיוטה להמשך או ביטול המעבר.

פערי כיסוי מוצגים לצד המונים: ״כל הפרומפטים שנאספו סווגו״ אינו ״כל השיחה נקלטה״. כשאין פרומפטים, מופיע מצב ריק שמסביר שאין נתונים לסיווג, ולא הודעת הצלחה על כיסוי מלא.

## המשמעות של שמירה, דילוג וניקוי

| מצב/פעולה | משמעות נתונית |
| --- | --- |
| טרם סווג | אין סיווג אנושי תקף; סוג וסיבות אינם מומצאים |
| שמירה | סוג ראשי תקף שנבחר או אושר במפורש; הסיבות נשמרות כפי שסופקו |
| דילוג | החלטה לחזור מאוחר יותר; לא שווה ל־irrelevant ולא הופך לסיווג אנושי |
| לא רלוונטי | סיווג אנושי תקף מסוג irrelevant; הפרומפט נשאר בהיסטוריה |
| תיקון סיווג | גרסה אנושית חדשה; הקודמת נשארת בהיסטוריה |
| ניקוי סיווג | ביטול התוקף של הסיווג האנושי האחרון; הפרומפט חוזר לתור ללא סיווג |
| טיוטה | עבודה מקומית שטרם נשמרה; אינה חלק מתוצאות הסיווג המאושרות |

דילוג נרשם רק לפרומפט שאין לו סיווג אנושי תקף. עבור פרומפט מסווג, ״הבא״ הוא ניווט בלבד ואינו מנקה את הסיווג. כפתור ״נקה סיווג״ הוא פעולה מפורשת ונפרדת; אינו מוחק את הפרומפט, את ההיסטוריה או הצעות מודל.

המונים יחושבו ממצב נוכחי, ולא ממספר אירועי האישור: שלושה תיקונים לפרומפט אחד הם עדיין פרומפט מסווג אחד. כיסוי סוגים וכיסוי סיבות מוצגים בנפרד; סיווג סוג עם reasons=null אינו מוצג כאילו נבדקו גם הסיבות.

## הצעת מודל לעומת החלטת משתמש

הפאנל אינו יוצר הצעות ואינו פונה למודל. הוא מציג הצעות שנשמרו באמצעות ממשק קיים או עתידי. הצעה אינה נבחרת כברירת מחדל בטופס ריק ואינה נספרת כסיווג אנושי.

המשתמש יכול ״העתק לטיוטה״ ולערוך, או ללחוץ במפורש ״אשר הצעה ושמור״ כאשר ההצעה המוצגת תקפה ושלמה. הפעולה יוצרת אירוע אנושי חדש שמפנה למזהה ההצעה שהוצגה. הצעה לא תקפה, טקסונומיה לא נתמכת או other חסר מועתקים לכל היותר לטיוטה עם צורך בתיקון, ולא נשמרים באמצעות אישור אוטומטי.

הצעה חדשה שהגיעה אחרי אישור אנושי אינה מחליפה אותו. הצעה שהגיעה במהלך עריכת טיוטה מציגה חיווי ״הצעה חדשה זמינה״ ואינה משנה את שדות הטופס. אישור הצעה ישנה שהמשתמש עדיין רואה מתייחס למזהה הישן הזה, ולא להצעה החדשה ברקע.

מקור ההחלטה יהיה human עבור פעולות הפאנל ו־model עבור הצעות. זהו מקור מדווח של הפעולה, לא הוכחה קריפטוגרפית לזהות האדם. אם להצעה ישנה חסרים שם מסווג, מודל או גרסה, מציגים ״לא נמסר״; אין להסיק אותם ממודל יצירת המצגת.

## שמירה, התנגשויות והתאוששות

מצב הסיווג האנושי נפרד מ־revision של מחזור חיי המחקר ומרצף הצעות המודל. לכל פרומפט נשמר `human_head_event_id`: מזהה פעולת הסיווג האנושית האחרונה, או null אם לא הייתה. save, skip ו־clear מקבלים את הראש שהוצג למשתמש באמצעות `expected_human_head`.

הבדיקה, הוספת האירוע ועדכון המצב נעשים בטרנזקציה אחת. שני חלונות שפתחו אותו ראש לא ידרסו זה את זה: הראשון מצליח והשני מקבל `classification_conflict`. הטיוטה של השני נשמרת, מוצגים הסיווג החדש והטיוטה שלו, והוא יכול לערוך ולשמור על בסיס הראש העדכני. הצעת מודל אינה משנה human_head ואינה מייצרת התנגשות אנושית מיותרת.

לכל פעולת כתיבה יש request ID יציב. fingerprint כולל פעולה, מחקר, פרומפט ותוכן, בצורה בלתי תלויה בסדר מפתחות JSON. retry לאחר תשובה שאבדה מחזיר את התוצאה המקורית. אותו request ID עם פרמטרים שונים נדחה. ״שמור והבא״ מתקדם רק לאחר שהשרת אישר שמירה.

טיוטות נשמרות מקומית בתוסף לפי project/session/prompt, עם הראש שעליו התחילו. הודעת ״טיוטה נשמרה״ תוצג רק לאחר שמירתה בפועל; היא אינה ״הסיווג נשמר״. סגירה רגילה שומרת טיוטה או מציעה טיפול בה, ובפתיחה מחדש מוצעת חזרה אליה. קריסה לפני שהטיוטה נשמרה יכולה לאבד את הקלט האחרון שלא נשמר; אין הבטחת אפס אובדן של הקלדה אחרונה. טיוטות אינן מיוצאות כנתוני מחקר מאושרים.

בקשת שמירה עם תוצאה לא ידועה נשמרת כפעולה ממתינה, בדומה לניהול המחקרים. היא נשלחת שוב רק עם אותו request ID ואותם פרמטרים, לא כפעולת שמירה חדשה. אחרי נפילה לפני commit אין חצי סיווג; אחרי commit ולפני תשובה יש אותה גרסה אחת. כשל אחסון או רענון לא מסומן כהצלחה ואינו מנקה את הטיוטה. שחזור טיוטה מול ראש שהשתנה מחייב יישוב התנגשות לפני שמירה.

פאנל לא מעביר תשובת שמירה ישנה לפרומפט או למחקר שנבחרו בינתיים. callbacks נבדקים לפי מזהי פרויקט/מחקר/פרומפט ובקשה, והמונים מתעדכנים מתשובה תקפה או מקריאה חדשה.

## נתונים ושירות מוצעים

אירועי הסיווג נשארים append-only. לא מעדכנים את `classification` המקורי בפרומפט כדי למחוק היסטוריה.

| אירוע | נתונים מרכזיים |
| --- | --- |
| `classification.confirmed` | סוג, סיבות או null, other, taxonomy_version, ראש אנושי קודם, request ID, מקור הפעולה והצעה ששימשה בסיס אם קיימת |
| `classification.skipped` | מחקר ופרומפט, ראש קודם, request ID; ללא תווית סיווג מומצאת |
| `classification.cleared` | ראש קודם, request ID; שומר את ההיסטוריה ומבטל סיווג נוכחי |
| `classification.suggested` | הצעה, taxonomy_version ומטא־דאטה מותר של מסווג: שם/גרסה ומודל אם נמסרו |

אירועים קיימים נקראים כפי שהם. אישור legacy עם prompt_type=null מפורש כאין סיווג תקף, ולא מומר אוטומטית לדילוג. אישור ישן עם סיבות null נשאר חסר סיבות. סדר seq משמש לסדר בתוך ledger; אין הסקה שאישור אנושי התייחס להצעת מודל מסוימת אם אין אליו קישור מפורש.

אפשר להוסיף projection בשם `prompt_annotations` עם human_head, מצב התור וראש הצעת המודל. הוא ניתן לבנייה מחדש מהאירועים באותה תוצאה. רשומת receipt לפעולות הסיווג תשתמש במנגנון בקשות יציב משותף עם namespace של classification, ולא בטבלת מצב בתוך ה־webview. לא מוסיפים בסיס נתונים נפרד.

קריאה, דילוג, ניקוי ושמירה עוברים דרך שירות Python אחד, חדש: `prompt_classifications.py`. אותו שירות משמש RPC, CLI ו־MCP. פעולותיו אינן נרשמות כפעולות יצירת מצגת ואינן מפעילות כלי Manim. שמירת סיווג אנושי מפורש של פרומפט קיים תותר גם כשאיסוף השיחה מושבת, בלי להפעיל אותו שוב; זהו שינוי נדרש לעומת `_require_enabled` הקיים ב־classify. אין יצירת מחקר או ייבוא תוכן חדש כתופעת לוואי של פתיחת הפאנל.

לתוסף יהיה חיבור RPC ייעודי לסיווג, בתהליך נפרד מתהליך ה־authoring RPC הקיים. אפשר להוסיף מסלול `studio research rpc` ולהשתמש בתשתית הבקשות/timeout הקיימת עם ארגומנטים מתאימים; לוגיקת הסיווג נשארת בשירות Python המשותף. אין להעביר קריאות סיווג איטיות דרך תור היצירה הסינכרוני הקיים ולהסתפק בכך שהכפתור אינו modal.

הכתיבה למסד קצרה: אין קריאת קבצים, רינדור או בקשת מודל בתוך טרנזקציית שמירת סיווג. זמן ההמתנה לנעילה יהיה מוגבל וניתן לבדיקה, וכשל מחזיר טיוטה/בקשה ממתינה במקום לחסום את הצ׳אט. הפרדת התהליכים אינה מבטלת נעילות SQLite; בדיקת עומס/כשל חייבת לוודא שלא נוספה תלות של היצירה בשמירת סיווג. אי־זמינות כללית של מסד התיעוד ממשיכה להיות מטופלת כפער איסוף לפי מדיניות ה־ledger הקיים, ולא מוצגת כשמירת סיווג מוצלחת.

| פעולה לוגית | תפקיד |
| --- | --- |
| `classification.schema` | סוגים, סיבות, תוויות וגרסאות נתמכות |
| `classification.list` | תור במחקר נתון לפי מצב, עם pagination ומונים |
| `classification.get` | פרומפט, הקשר, סיווג תקף, הצעות ו־human_head |
| `classification.history` | רצף סיווגים, דילוגים וניקויים לפרומפט |
| `classification.save` | שמירה אנושית עם expected_human_head ו־request_id |
| `classification.skip` | דילוג מפורש לפרומפט ללא סיווג |
| `classification.clear` | ניקוי מפורש של הסיווג התקף |

בגרסה זו יש פקודה חדשה אחת לכניסה לפאנל, למשל `manimStudio.research.classifyPrompts`. אין פקודת ״סווג את כל המחקר״ ואין אישור גורף של הצעות מודל.

### חוזה כתיבה ותאימות

קוראים היסטוריים וייצוא קיימים ממשיכים לעבוד. יש להרחיב את classify הקיים או לנתב אותו לשירות המשותף, כך שלא יישאר נתיב כתיבה אנושי שעוקף את בדיקת הראש. כתיבה אנושית דרך CLI/MCP בגרסה החדשה מחייבת request ID ו־expected_human_head, כולל null מפורש בכתיבה ראשונה. לקוח כתיבה ישן שחסרים לו שדות אלה יקבל שגיאה מובנית והנחיה לקרוא את המצב תחילה; לא תתבצע שמירה עיוורת לשם תאימות.

זו התאמת חוזה כתיבה מתוכננת, לא שינוי בנתונים הישנים. יש לעדכן את schema/תיעוד הכלי ואת קריאות בדיקות האינטגרציה הקיימות בהתאם. אין הבטחת תמיכה בכותבים מתהליכים ישנים שמתחברים ישירות לאותו מסד בלי בדיקת גרסה. הצעת מודל נשארת נפרדת ואינה יכולה להפוך להחלטה אנושית באמצעות עקיפת שירות זה.

כל כתיבה מאמתת שהפרומפט שייך למחקר ולפרויקט, שסוגו יחיד ומוכר, שהסיבות חוקיות ושהטקסט other תקין. מחקר אחר עם שם זהה אינו יעד חלופי. שגיאות צפויות: `prompt_not_found`, `project_mismatch`, `classification_conflict`, `classification_revision_required`, `request_id_conflict`, `invalid_classification`, `unsupported_taxonomy`, `storage_error`.

## קריאה, ייצוא ותצוגה בטוחה

pagination וסינון נעשים בשרת. snapshot_seq מגדיר תמונת רשימה ומונים לאותה קריאה; תוספת פרומפטים ברקע מוצגת ברענון מפורש/מחזורי בלי שינוי סדר ההודעות שכבר מוצגות. הסדר הבסיסי הוא seq של אירועי המקור. הפרומפט הבא לאחר שמירה נבחר לפי המסנן והזהויות, ולא לפי אינדקס שהשתנה ברקע.

ייצוא מלא כולל את אירועי ההיסטוריה ואת שדות המקור/הגרסה הדרושים לשחזור. ייצוא מטא־דאטה ממשיך להשמיט תוכן פרומפטים ופירוט other, ושומר תוויות, מזהים וגרסת טקסונומיה מותרים. לא מייצאים הגדרות מודל שרירותיות או סודות עם ״מטא־דאטה של מסווג״. לא מוסיפים מסך ייצוא חדש בפיצ׳ר זה.

הסיווג התקף נקבע לפי הפעולה האנושית התקפה האחרונה, ולא לפי האירוע האחרון מכל מקור. לצורך שחזור אחרי clear או תיקון, מפענחים את ההיסטוריה עם אותה גרסת טקסונומיה. אין ייצוא שבו הצעת מודל ממלאת אוטומטית ערך אנושי חסר.

תוכן מקור והצעות מוצגים כטקסט, עם CSP והפרדה מקוד ה־webview. הודעות מה־webview מאומתות בשרת; מזהי בקשה ופרומפט שמגיעים ממנו אינם נחשבים ראיה לשיוך תקין ללא בדיקה במסד. קישורי קבצים או פעולות שיוצגו בהקשר הם לקריאה בלבד בפיצ׳ר זה.

## סדר מימוש

1. שירות הקריאה והמצב התקף, עם fixtures של היסטוריה ישנה, אישורים והצעות מעורבים.
2. כתיבות save/skip/clear אטומיות, request receipts ובדיקות שני כותבים. עדכון נתיב classify הישן לחוזה המוגן.
3. חשיפה ב־RPC ייעודי/CLI/MCP ועדכון ייצוא עבור האירועים ושדות הטקסונומיה החדשים; בדיקה שבקשת סיווג תקועה אינה תופסת את תור היצירה.
4. פאנל VS Code עם רשימה, מסננים, הקשר, טופס והיסטוריה. תחילה סיווג אנושי, ואז הצגת/אישור הצעות קיימות ללא מסווג אוטומטי.
5. טיוטות, התאוששות מ־timeout, חזרה אחרי סגירה, ושיחה שממשיכה בזמן שהפאנל פתוח.
6. אינטגרציה ובדיקת קבלה ב־VS Code האמיתי על Windows.

## תנאי הצלחה ובדיקות קבלה

הבדיקה תשתמש בנתוני מקור ובתסריט צפויים מראש: שני מחקרים, פרומפטי פתיחה/המשך/תיקון/לא־רלוונטי, כמה סיבות, other, הצעות מודל, סיווגים ישנים ותיקוני סיווג. המצב הצפוי מחושב בנפרד מתשובת רשימת התור של השירות.

| מדד | תנאי מעבר |
| --- | --- |
| עבודה שאינה נחסמת | אפשר לשלוח פרומפט ולבצע פעולת יצירה כשהפאנל סגור, פתוח, עם טיוטה או עם שמירת סיווג שנכשלה; אין תלות של מסלול היצירה בתשובת מסלול הסיווג |
| שיוך | אפס סיווגים למחקר/פרומפט שגויים, לרבות החלפת בחירה ותגובה מאוחרת |
| תוויות | בכל תרחיש מבוקר נשמר בדיוק הסוג היחיד והסיבות שנבחרו; null, רשימה ריקה ו־other נשארים מובחנים |
| דילוג וניקוי | skip אינו irrelevant או אישור; clear מבטל סיווג נוכחי בלי למחוק פרומפט או היסטוריה |
| מקור | אפס הצעות שנספרות כאישור אנושי ללא פעולה מפורשת; הצעה מאוחרת אינה מחליפה אישור |
| היסטוריה | כל תיקון נשאר קריא, והמצב התקף זהה אחרי בנייה מחדש מהאירועים וקריאת ייצוא מלא |
| כותבים מקבילים | שתי שמירות מאותו human_head מניבות הצלחה אחת והתנגשות אחת, בלי דריסה אבודה ובלי מחיקת הטיוטה של הכותב השני |
| נפילה/retry | לפני commit אין חצי סיווג; אחרי commit ותשובה שאבדה מתקבלת גרסה אחת בלבד עם אותו request ID |
| חידוש עבודה | טיוטה שנשמרה, בחירת מחקר ופרומפט ובקשה ממתינה חוזרים לאחר פתיחה מחדש, בלי להעביר אותם למחקר אחר |
| מונים | 100% התאמה לתסריט הצפוי, כולל כמה תיקונים לאותו פרומפט ודילוגים; ריק או כיסוי חלקי אינם מוצגים כשיחה מלאה שסווגה |
| ממשק בפועל | אפשר לסווג, לתקן, לדלג, לנקות ולאשר הצעה ב־VS Code בלי JSON ובלי לשנות את שיחת Codex |

יש להריץ בדיקות שירות ו־transport ב־Linux וב־Windows CI, בדיקות התנהגות של התוסף, ובדיקת קבלה בפאנל האמיתי על Windows. הזרקות כשל יכללו כשל מסד, תשובה שאבדה, callback ישן ושחזור טיוטה שהראש שלה כבר הוחלף. קריאה ושמירה ייבדקו גם במחקר finished וכשאיסוף השיחה כבוי.

לגרסה ראשונה אין יעד מספרי מומצא של ״שניות לסיווג״. לא מופיעים דיאלוגים לכל פרומפט, סוג נבחר בפעולה אחת וסיבות בכמה בחירות לפי הצורך. במהלך 8–10 התהליכים אפשר לאסוף משוב על עומס התיוג; לא מסיקים זמן עבודה אנושי מהפרש בין הודעות ולא מוסיפים כאן מערכת מדידת זמן.

הפיצ׳ר ייסגר רק אחרי מעבר תנאי הקבלה, לרבות הממשק האמיתי. סגירתו אינה סוגרת פערי קליטת שיחה מפיצ׳ר 1, ואינה קובעת שסיבות מדווחות הביאו לשיפור באיכות המצגת.
