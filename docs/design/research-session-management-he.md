# דיזיין: ניהול סשני מחקר ב־VS Code

תאריך: 31.10.2026  
ענף בסיס: `research/prompt-logging`, קוד `41eff56`  
סטטוס: מימוש מקומי לפיצ׳ר 2; 132 בדיקות Python ובדיקות התוסף עברו. המימוש מוכן להעלאה לענף המחקר; אימות הלקוח האמיתי נשאר פתוח. אימות בלקוח Codex וב־VS Code האמיתיים על Windows נשאר פתוח. ראו [דוח האימות](../concepts/research-session-management-validation-he.md).

## מטרה וחוויית השימוש

לאפשר למשתמש לנהל מתוך VS Code תהליך מחקר בנושא מוגדר: להתחיל, לחבר את השיחה והכלים, להשהות, להמשיך ולסיים. כל ההודעות והפעולות שנאספות יישארו משויכות לתהליך הנכון גם אחרי הפעלה מחדש ובזמן ששני תהליכים פתוחים במקביל.

לדוגמה: המשתמש פותח מחקר בשם ״מרחק בין וקטורים — ניסיון 1״, מחבר אליו שיחת Codex וטרמינל, ועובד כרגיל. למחרת הוא חוזר לאותו מחקר וממשיך עם אותם מזהים. עבודה בנושא אחר נפתחת כמחקר נפרד, גם אם היא מתבצעת באותו פרויקט.

סשן מחקר מתאר את יחידת התיעוד של הניסוי. סשן יצירה מתאר את תהליך בניית המצגת הקיים. הם מזהים נפרדים עם מחזורי חיים נפרדים: סיום מחקר אינו סוגר מצגת, והשהיית יצירה אינה מפסיקה את תיעוד המחקר.

`research_session_id` הוא UUID שנוצר פעם אחת לכל ניסיון מחקר ונשמר מתחילתו ועד סופו, גם לאורך כמה ימים, השהיות, הפעלות מחדש ונפילות. החידוש אינו יוצר ניסיון חדש. לכל פרומפט ופעולה יש מזהה נפרד שמקושר למחקר; נושא זהה או שם זהה אינם הופכים שני ניסיונות לאותו מחקר. ה־UUID אינו מזהה של חלון VS Code או של תהליך מערכת הפעלה.

## מה כבר קיים ומה צריך להשתנות

| רכיב קיים | שימוש בדיזיין |
| --- | --- |
| `research.py`: SQLite, אירועים, מזהי סשן ופרומפט | נשאר מקור האמת לתיעוד; תתווסף שכבת ניהול באותו מסד |
| `research_capture.py`: מיפוי עמיד מ־Codex thread לסשן מחקר | נשמר; ניהול מפורש יתווסף בלי להעביר הודעות ישנות בין סשנים |
| `configure(enabled)`: מתג איסוף ברמת הפרויקט | נשאר מתג כללי; מתווספת השהיה עצמאית לכל מחקר |
| `research_cli.py` ו־MCP `research_log` | יעבירו את אותן פעולות ניהול לאותו שירות Python |
| RPC עם `_research` ומשתני סביבה של מחקר | יורחבו להקשר מפורש של לקוח, עם בדיקת התוקף במסד לכל בקשה |
| פקודות הסשנים בתוסף | יישארו פקודות יצירה; פקודות המחקר יקבלו שמות ותצוגה נפרדים |
| טרמינל יחיד בתוסף, ללא הקשר מחקר מפורש | יוחלף בניהול טרמינלים המשויכים למחקרים |

היום המיפוי האוטומטי של thread יוצר סשן ללא בחירת נושא. הוספת כפתור Start שמייצר מזהה נוסף לבדה תיצור שני סשנים לאותו תהליך; הדיזיין מגדיר איך מחברים אותם בלי מיזוג היסטוריה בדיעבד.

## החלטות לגרסה הראשונה

1. SQLite הוא מקור האמת. מצב התוסף הוא בחירת תצוגה בלבד.
2. לכל מחקר מנוהל יש לכל היותר שיחת Codex אחת. אפשר לחבר אליו כמה לקוחות, למשל RPC, MCP וטרמינל. כמה מחקרים יכולים לפעול במקביל באותו פרויקט.
3. שיחת Codex שכבר שויכה למחקר אינה מועברת למחקר אחר בגרסה זו. לנושא חדש פותחים שיחה חדשה. חידוש אותה שיחה ממשיך את אותו מחקר.
4. החלפת המחקר המוצג אינה משנה שיוך של שיחה, טרמינל או פעולה שכבר התחילה.
5. אין הסקה של הפרומפט לפי ״הפרומפט האחרון״. פעולה עם מחקר מזוהה ופרומפט חסר נשמרת עם `prompt_id=null`.
6. השהיה וסיום מפסיקים איסוף תוכן חדש למחקר, אך אינם חוסמים את עבודת המשתמש או כלי היצירה.
7. הצלחת פקודת Start אינה ראיה שהלקוח מוסר אירועים. מוכנות הסשן ואיכות האיסוף יוצגו בנפרד.

הגבלה מפורשת: ניהול כמה שיחות Codex בתוך אותו מחקר או העברת אותה שיחה בין נושאים הם הרחבה עתידית. הם אינם נדרשים לבדיקת שני תהליכים נפרדים במקביל.

## התנגשויות במצב המחקר ובקבצי העבודה

יש להבחין בין שלושה מקרים:

| התנגשות | מענה בגרסה זו |
| --- | --- |
| שני חלונות מעדכנים את אותו מחקר | טרנזקציה ובדיקת revision; כותב אחד מצליח והשני מרענן מצב |
| אותה שיחה או אותו לקוח משויכים לשני מחקרים | אילוץ ייחודיות ושגיאה מפורשת; אין העברה או מיזוג בשקט |
| שני תהליכים עורכים את אותם קבצי מצגת | הפרדת לוגים אינה מונעת דריסת קבצים; אין הבטחת עריכה מקבילה בטוחה באותה תיקייה |

לעבודה מקבילה אמיתית שמשנה קבצים, ההמלצה היא תיקיות פרויקט או worktrees נפרדים. באותו פרויקט אפשר לנהל כמה מחקרים ולהפריד את התיעוד, אך יש לתאם את הכתיבה לקבצים. הממשק יציין את המגבלה כאשר פועלים כמה מחקרים באותה תיקייה; לא יבטיח נעילה של עריכות ידניות או של תהליכים חיצוניים. מנגנון כללי לנעילת קבצים או מיזוג עריכות אינו חלק מהפיצ׳ר.

בדיקת שני המחקרים באותו פרויקט תוכיח בידוד של תיעוד ומצב; היא תשתמש בפעולות קריאה או בקבצים נפרדים. בדיקה של שני תהליכי יצירה אמיתיים במקביל תתבצע בתיקיות נפרדות. הצלחה בראשונה לא תיחשב הוכחה שאין התנגשויות קבצים בשנייה.

## תהליך העבודה בממשק

### התחלה וחיבור שיחה

פקודה `Research: Start Session` מבקשת שם ניסיון ונושא. הנושא הוא טקסט חופשי, עם בחירה נוחה מנושאים שכבר הוזנו בפרויקט. שמות זהים מותרים; UUID מבדיל בין ניסיונות.

נוצר מחקר במצב `active`, עם חיווי ״ממתין לחיבור שיחה״. לאחר מכן מוצגת בחירת שיחת Codex שנצפתה בפרויקט: מזהה מקוצר, מקור זמין וזמן אירוע אחרון. אין הנחה שלתוסף שלנו יש API שמחזיר את השיחה הפעילה של תוסף Codex.

אם עדיין לא נצפתה שיחה, הממשק מסביר שיש לפתוח שיחה ולהפעיל רענון. אין שיוך אוטומטי של ״השיחה הבאה״, כי שני חלונות עלולים להיפתח יחד. השיחה מזוהה מתוך אירועי המתאם בלבד; לא סורקים היסטוריות משתמש.

במצב ניהול מפורש, מקור חדש ולא משויך נרשם לצורכי זיהוי כמטא־דאטה בלבד, בלי שמירת תוכן הפרומפטים. החיבור מציב גבול איסוף מפורש: ממשיכים מהנקודה הנוכחית, בלי לייבא את מה שנאמר לפני החיבור. לכן המשתמש ישלח את פרומפט המחקר הראשון רק לאחר החיבור. חיבור באמצע שיחה יסומן כתחילת כיסוי מאוחרת.

שיחה שכבר שויכה למחקר מנוהל מציעה מעבר למחקר שלה. עבור סשן שנוצר במתאם הישן אפשר לבחור ״המשך תיעוד קיים״, לתת שם ונושא ולנהל את אותו `session_id`; האירועים הישנים נשארים, ונשמר אירוע שמציין ממתי נוסף ניהול מפורש. אין פעולה שקטה שממזגת אותו עם מחקר חדש.

### השהיה, חידוש וסיום

- **Pause:** משהה את המחקר הנבחר בלבד. מחקר אחר באותו פרויקט ממשיך להיאסף.
- **Resume:** ממשיך את אותו מזהה; תוכן מתקופת ההשהיה אינו נאסף בדיעבד.
- **Finish:** מסיים את המחקר ומציג סיכום קצר: נושא, מספר פרומפטים, פעולות ופערי כיסוי ידועים. אינו מודד זמן עבודה אנושי.
- מחקר שהסתיים הוא לקריאה בלבד מבחינת איסוף תוכן. אפשר לסווג פרומפטים ישנים דרך הממשק הקיים; סיום אינו מוחק נתונים ואינו מונע סיווג בדיעבד.
- סגירת חלון VS Code אינה מסיימת או משהה מחקר אוטומטית: לקוח אחר עשוי עדיין לעבוד. בפתיחה מחדש משחזרים את המצב מהמסד.
- אירוע `SessionEnd` של Codex מסמן ניתוק של מקור השיחה; אינו מסיים את המחקר. חידוש אותו thread מחבר שוב את אותו מקור.

### תצוגה

תתווסף שורת מצב נפרדת, למשל `Research: Vectors · Active`. לחיצה פותחת Quick Pick של פעולות המחקר. הפקודות יהיו תחת namespace נפרד, למשל `manimStudio.research.startSession`, כדי שלא יתערבבו עם Start/Pause/Finish של היצירה.

פקודת `Research: Show Status` תציג בפאנל פשוט:

| ממד | דוגמאות |
| --- | --- |
| מצב המחקר | פעיל, מושהה, הסתיים |
| חיבור שיחה | לא חוברה שיחה, מקור נצפה, מנותק, מצב לא ידוע |
| היקף האיסוף | hooks בלבד, hooks ותמליל במאמץ מיטבי, חלקי |
| עדכניות | זמן האירוע האחרון וזמן הרענון האחרון |
| כשלים | פערים משויכים למחקר וכשלים ללא שיוך ברמת הפרויקט |
| לקוחות | שיחת Codex, טרמינלים ולקוחות נוספים עם מזהים מקוצרים |

״אין אירוע חדש זמן רב״ יוצג כמידע על עדכניות, ולא כהוכחה לניתוק. שיחה שקטה יכולה להיות תקינה. כשל רענון יציג ״המצב אינו מעודכן״ ולא יהפוך את המצב האחרון לראיה שהאיסוף עובד.

אין חלונית סיווג, אין צ׳אט חדש ואין הודעה אחרי כל פרומפט. עדכון תצוגה באמצעות polling מתון, למשל כל 5 שניות כשהחלון ממוקד, עם מניעת בקשות חופפות והאטה בכשל. פעולת ניהול מרעננת מיד לאחר תשובה מוצלחת.

## מחזור חיים ואטומיות

| מצב | פעולה | מצב חדש | התנהגות |
| --- | --- | --- | --- |
| אין מחקר | create | active | עדיין אין איסוף שיחה עד חיבור מקור |
| active | pause | paused | פסק זמן באיסוף של מחקר זה בלבד |
| paused | resume | active | אותו UUID, תקופת איסוף חדשה |
| active / paused | finish | finished | הפסקת איסוף תוכן חדש וסיכום |
| finished | resume | ללא שינוי | שגיאת `session_finished`; יש ליצור ניסיון חדש |

בחירת מחקר אחר בממשק אינה מעבר מצב. קריאה חוזרת ל־pause או finish לא תוסיף אירועי מעבר כפולים.

כל שינוי מצב, העלאת `revision` ואירוע ניהול נשמרים בטרנזקציה אחת. כל פעולת שינוי מגיעה עם `request_id` יציב ו־`expected_revision`; ניסיון חוזר לאחר timeout מחזיר את התוצאה המקורית. שני חלונות שמשנים אותו מחקר יגלו התנגשות גרסאות וירעננו מצב, במקום לדרוס זה את זה.

ה־UI מציג הצלחה רק לאחר commit למסד. כשל תיעוד אינו מציג ״הושהה״ או ״הסתיים״ אם השינוי לא נשמר. אין באגירת מצב מקומית כדי להתגבר על כשל כזה.

## עצירה באמצע והתאוששות מנפילות

כל האירועים והתוכן שכבר נשמרו, הסיווגים והקישורים לגרסאות שנאספו נשארים אחרי השהיה, סגירת חלון ונפילה. סיום מחקר גם הוא אינו פעולת מחיקה. אין כאן הבטחה לארכוב מלא של כל תוצרי המצגת: כיסוי הקבצים ומדיניות שימור התוצרים נשארים בגבולות מנגנון האיסוף הקיים והפיצ׳רים הבאים.

פתיחה מחדש קוראת את מסד הנתונים, משחזרת את רשימת המחקרים, מצבם והשיוכים, ובודקת את המקורות לפני הצגת מצב איסוף מעודכן. בחירת תצוגה שמורה שלא נמצאת במסד מבוטלת; היא אינה יוצרת מחקר חדש כתחליף. אין צורך לפתוח מחדש ניסיון רק משום שתהליך התוסף התחלף.

| נקודת הנפילה | המצב המחייב לאחר חזרה |
| --- | --- |
| לפני commit של יצירה או שינוי מצב | השינוי לא נחשב שמור; אין חיווי הצלחה או יצירה חלופית אוטומטית |
| אחרי commit ולפני מסירת התשובה ללקוח | retry עם אותו request ID מחזיר אותה תוצאה ואותו UUID, בלי אירוע ניהול כפול |
| באמצע טרנזקציית אירוע ו־cursor | נשמרים יחד או מתבטלים יחד; מקור שניתן לקריאה חוזרת ייקרא מהמיקום האחרון שנשמר |
| אחרי תחילת פעולה ולפני תיעוד הסיום | הפעולה מסומנת כ״הסיום לא אומת״; לא כהצלחה ולא ככישלון מוכח |
| כשל כתיבה או מסד שאינו זמין | מוצג כשל שמירה/מצב לא ידוע; אין מעבר אוטומטי ל־UI שמציג איסוף תקין |

התאוששות מתיעוד אינה הפעלה מחדש של הפעולה עצמה. המערכת לא מריצה שוב עריכה, accept, פקודת shell או render באופן אוטומטי רק מפני שלא נצפה סיום; ייתכן שהפעולה כבר בוצעה. אם צריך, המשתמש בודק את מצב התוצר ומחליט כיצד להמשיך. תהליך חיצוני או מידע שלא נשמר בדיסק אינם משוחזרים מכוח חידוש המחקר בלבד.

גבול ההבטחה הוא המצב האחרון שנשמר בהצלחה. מידע שהגיע לפני commit עשוי להידרש לקריאה חוזרת ממקור האירועים. אם המקור אינו זמין, מציגים פער או כיסוי שלא אומת. אין הבטחה לאפס אובדן בכל נפילה או לזיהוי כל אירוע שלקוח חיצוני כלל לא מסר; אירוע שלא הותיר כל ראיה אינו ניתן לשחזור מהמסד לבדו. חיווי ״אין פער מזוהה״ אינו תעודת שלמות.

## מודל נתונים מוצע

מיגרציה תוספתית לסכמה הבאה, ללא שינוי מזהים או כתיבה מחדש של אירועים היסטוריים.

| ישות | שדות ותפקיד |
| --- | --- |
| `research_sessions` | `session_id`, שם, נושא, מצב, `revision`, `capture_epoch`, זמני יצירה/עדכון/סיום, ציון legacy או managed |
| `research_sources` | `source_id`, project ID, thread ID, session ID אופציונלי, זמן תצפית אחרון וגבולות כיסוי; מפתח ייחודי לסוג מקור ו־thread בפרויקט |
| `research_clients` | client ID, project ID, session ID, סוג לקוח; שיוך מפורש ל־RPC/MCP/טרמינל |
| `research_requests` | request ID, טביעת פרמטרים ותוצאה של פעולת ניהול; למניעת יצירה/מעברים כפולים בניסיונות חוזרים |
| טבלאות capture הקיימות | ממשיכות להחזיק cursor, קבלות ניכוי כפילויות ומצב קליטה של מקורות משויכים |
| אירועי `session.*` | היסטוריית יצירה, מתן נושא, אימוץ סשן ישן, חיבור מקור, השהיה, חידוש וסיום |

אירוע `session.started` הקיים ממשיך להיות אירוע הזהות של המחקר; הכנסת רשומת הניהול נעשית באותה טרנזקציה. אין יצירה של אירוע started שני לאותו UUID. לסשן legacy קיים מוסיפים רשומת ניהול שמפנה ל־UUID הקיים, ואירוע אימוץ חדש בלבד.

`research_sources` מאפשר לזהות thread שטרם חובר בלי ליצור עבורו סשן מחקר מלא ובלי לשמור תוכן שיחה. לאחר חיבורו נוצרת גם רשומת ה־capture הדרושה, עם cursor התחלתי בנקודת החיבור.

בתצורת legacy המיפוי האוטומטי הקיים נשאר תקף. מעבר לניהול מפורש הוא פעולה מודעת, מציג שיחות ישנות לבחירה, ואינו מפסיק או מאמץ אותן בשקט. במצב managed מקורות חדשים ממתינים לחיבור. המצב נשמר במסד; מתאם ישן שאינו תומך בו אינו מוכרז כתואם — נדרשת בדיקת יכולת/גרסת סכמה לפני הפעלת ניהול מפורש.

בחירת הסשן המוצג נשמרת ב־VS Code workspace state תחת מפתח חדש. היא אינה שדה ״סשן גלובלי פעיל״ במסד ואינה מנגנון לניתוב אירועים. בגרסה זו נשמרת מגבלת התוסף הקיימת: תיקיית workspace ראשית אחת; תמיכה מלאה ב־multi-root אינה נכללת.

## שיוך בין התוסף, MCP והטרמינל

כל לקוח משויך למחקר באמצעות מזהה מפורש. לכל פעולה נקבע ההקשר בעת קבלתה; שינוי בחירת ה־UI באמצע הפעולה אינו משנה אותו.

- **Codex:** המפתח הוא project ID ו־thread ID שנצפה. מיפוי קיים למחקר נשמר לאחר סגירה וחידוש. אין שיוך לפי ״החלון הפעיל״.
- **RPC של התוסף:** נשלח `_research` ברמת הבקשה, בנפרד מהפרמטרים של פעולת היצירה. נשמרים client ID ו־session ID. prompt ID נשלח רק כשהוא ידוע במפורש, ולא נלקח משורת המצב.
- **MCP:** נשמרים הפרמטרים הקיימים `research_session_id` ו־`research_prompt_id`; יתווסף הקשר client מפורש לפי הצורך. השרת בודק project, session ומצב עדכני בכל בקשה. שרת שכבר רץ אינו ״מסתנכרן״ רק כי השתנה משתנה סביבה בחלון אחר.
- **טרמינל:** הפקודה `Research: Open Terminal` יוצרת טרמינל המשויך למחקר ובעל client ID קבוע. אפשר לפתוח טרמינל למחקר אחר בלי לשנות את הראשון. משתני סביבה מעבירים זהות מחקר ולקוח בלבד; לא מגדירים prompt ID גלובלי בטרמינל מתמשך.
- **לקוח ותיק ללא IDs:** ב־managed mode לא מנחשים הקשר. העבודה מתבצעת, ואי־השיוך מופיע באבחון ללא העתקת תוכן הפעולה למחקר שנבחר במקרה.

סדר ההכרעה: מזהים מפורשים בבקשה → שיוך לקוח מפורש → ללא שיוך. אם מזהה מפורש שגוי, זר או סותר את שיוך הלקוח, אין fallback למחקר אחר. כשל ההקשר מדווח, וכלי היצירה שומר על התנהגותו הרגילה. ב־legacy mode נשמרת תאימות למשתני הסביבה הקיימים, עם בדיקות תוקף וללא ערבוב עם managed mode.

בקשות ניהול המחקר עצמן אינן נרשמות כפעולות יצירת תוכן באמצעות wrapper המחקר הכללי; הן מייצרות את אירועי הניהול המפורשים שלהן. כך נמנעות רקורסיה וכפילויות תיעוד.

Hooks של Codex ועטיפות השירות יכולים לתעד גבולות חיצוניים ופנימיים של אותה עבודה. הדיזיין שומר את מקור האירוע ואת גבול התצפית; אינו ממציא התאמה בין שתי פעולות שאין להן מזהה קשר. מיזוג לניתוח סטטיסטי נמצא מחוץ לפיצ׳ר זה.

## השהיה, מידע מאוחר ופעולות שכבר התחילו

מתג האיסוף הכללי הוא תנאי ראשון. בנוסף נבדק מצב המחקר תחת אותה טרנזקציה שבה נרשם האירוע. אין הסתמכות על מטמון בתוסף כדי להחליט אם מותר לשמור תוכן.

להשהיה/חידוש יהיה epoch עצמאי למחקר, בנוסף ל־epoch הכללי הקיים. השהיית A לא משנה cursor או epoch של B. בחידוש מחקר מציבים גבול קליטה חדש לתמליל, ולא מייבאים הודעות מהתקופה המושהית. אם יש חוסר ודאות לגבי הודעות buffered סביב הגבול, מסמנים פער ולא מייחסים להן שלמות שלא הוכחה.

הפסקת איסוף מתייחסת לתצפיות על הודעות ופעולות מתקופת ההשהיה: הן לא ייובאו בדיעבד. אם אחרי חידוש נאספת תמונת מצב חדשה של קובץ, היא משקפת את הקובץ הנוכחי, שעשוי לכלול גם שינויים שנעשו בזמן ההשהיה; כך גם תוכן שהמשתמש שולח מחדש במפורש אחרי חידוש. אין הבטחה לסינון לפי זמן היצירה ההיסטורי של כל מחרוזת בתוך תוכן שנצפה מחדש בזמן איסוף פעיל.

מפת הפרומפטים המשמשת לשיוך תגובות לא חוצה epoch באופן שמאפשר להצמיד תשובה ישנה לפרומפט חדש. תשובה מאוחרת עם הקשר turn לא מתאים תסומן כפער; היא לא תשויך לפרומפט האחרון של המחקר. תוכן שנוצר בזמן ההשהיה לא ייאסף גם אם הגיע לאחר החידוש.

אירוע תחילת פעולה שומר session ID, prompt ID ו־epoch. סיום פעולה אינו משויך מחדש. אם הפעולה חוצה השהיה/סיום, אין לאסוף את תוכן התוצאה האסור; שומרים רק סימון מטא־דאטה שמסביר מדוע התצפית לא הושלמה, בלי לטעון שהפעולה עצמה נכשלה. הסיכום מציג פעולות שלא נצפה להן סיום.

סדר ב־SQLite מגדיר את גבול ההשהיה במקרה של מרוץ בין בקשות. זמן הגעת האירוע לשרת אינו מוצג כזמן המדויק שבו האדם פעל. סיום מחקר אינו ממתין בכפייה להשלמת render ואינו מבטל אותו.

## API מוצע

כל הממשקים משתמשים בשירות Python אחד; אין לוגיקת lifecycle נפרדת ב־TypeScript וב־MCP.

| פעולה לוגית | קלט עיקרי | תוצאה |
| --- | --- | --- |
| `research.create` | title, topic, request_id | session עם מצב active, ללא מקור עד לחיבור |
| `research.list` / `research.get` | מסננים / session_id | סשנים ומצב ניהול |
| `research.sources` | project נוכחי | מקורות שנצפו וסטטוס השיוך שלהם |
| `research.attach_source` | session_id, source_id, expected_revision, request_id | שיוך ראשון וגבול כיסוי |
| `research.adopt_legacy` | session_id קיים, title, topic, request_id | ניהול אותו תיעוד קיים; ללא העברת אירועים |
| `research.pause` / `resume` / `finish` | session_id, expected_revision, request_id | מצב מאושר, revision חדש וסיכום לפי הצורך |
| `research.bind_client` | session_id, client_id, client_type, request_id | שיוך יציב ללקוח חדש |
| `research.status` | session_id | מצב, מקורות, עדכניות, כיסוי ופערים |

ב־CLI וב־MCP `research_log` אפשר למפות שמות אלה לפעולות dispatch מפורשות; ב־RPC הם namespace נפרד מפעולות היצירה. צורת התוצאה תהיה אחידה ותכיל `revision`, ולא תחייב את התוסף לפרש טבלאות SQLite בעצמו.

שגיאות צפויות: `session_not_found`, `session_finished`, `revision_conflict`, `source_already_bound`, `project_mismatch`, `capture_disabled`, `unsupported_schema`, `storage_error`. אין תיוג מצב finished כ״פעיל״ באמצעות fallback משתנה סביבה ישן.

## סדר פיתוח ובדיקות קבלה

1. **שירות ומיגרציה:** lifecycle, events, idempotency ותאימות לתיעוד קיים. לבדוק שני חלונות עם revision זהה ושחזור לאחר commit שתשובתו אבדה.
2. **חיבור המתאם:** גילוי מקור וחיבורו, אימוץ legacy וגבולות השהיה. לבדוק שחיבור מאוחר אינו מייבא היסטוריה וש־A מושהה בלי להשפיע על B.
3. **RPC/MCP/טרמינל:** העברת הקשר מפורש, בדיקת מצבים ושימור שיוך לפעולות רצות. לבדוק תהליכים נפרדים, מזהים שגויים ומשתני סביבה ישנים.
4. **ממשק VS Code:** התחלה ובחירת נושא, חיבור שיחה, בחירת מחקר מוצג, השהיה/חידוש/סיום והצגת מצב שאינו מעודכן. לבדוק ביטול Quick Pick וסגירת חלון ללא שינוי lifecycle.
5. **בדיקה משולבת:** שני נושאים, שתי שיחות ושני טרמינלים; מחליפים את התצוגה בזמן פעולה; משהים מחקר אחד; סוגרים ופותחים VS Code; מחדשים את השיחה הנכונה ומסיימים. משווים אירועים, תמלילים וייצוא קיים כדי להוכיח שאין ערבוב.

בדיקות משמעותיות נוספות: התחלת פעולה לפני pause ותוצאה אחרי resume; מקור חדש בזמן שאין חיבור; session finished עם טרמינל שעדיין פתוח; כשל כתיבה בזמן Finish; callback ישן שמגיע לאחר מעבר UI למחקר אחר; פרומפט לא מזוהה שנשאר null; כמה פרומפטים באותו turn שנשארים עמומים; כשל רענון שלא מוצג כאיסוף תקין. בדיקות ההפסקה חייבות לוודא שהתוכן המושהה אינו מופיע גם בייצוא מלא.

תרחישי השירות וה־transport ירוצו אוטומטית ב־Linux וב־Windows CI. בדיקת קבלה בלקוח Codex וב־VS Code האמיתיים תישאר תנאי סגירה, עם גרסאות מתועדות. בדיקת התוסף באמצעות mocks אינה תחליף למסירת אירועים מהלקוח בפועל.

## תנאי סגירה וגבולות הפיצ׳ר

הפיצ׳ר ייסגר כאשר אפשר לנהל שני תהליכים במקביל, להשהות אחד ולהמשיך את השני, לחזור לאחר סגירה, ולשחזר מהתיעוד איזה מקור ולקוח השתייכו לכל מחקר — בלי חוסרים סמויים ובלי מעבר של אירוע למחקר שגוי. היעדר מסירה או פער יישארו גלויים גם כשה־UI מציג מחקר active.

### מדדי קבלה מחייבים

המדידה תתבסס על תסריט עם רשימת אירועים צפויה שנכתבה מראש ועל ראיות מקור נפרדות: ההודעות שנשלחו, תוצאות כלי הבדיקה ותמליל הלקוח כשהוא זמין. לא מחשבים שלמות רק מתוך האירועים שהמערכת הצליחה לשמור. שומרים את גרסאות הלקוח, המערכת והמימוש שנבדקו לצד תוצאות הבדיקה.

| מדד | תנאי מעבר בתרחיש המבוקר |
| --- | --- |
| זהות מחקר ורציפות | אותו UUID והיסטוריה שמורה אחרי Pause/Resume, סגירת חלון והפעלה מחדש; ניסיון חדש מקבל UUID שונה |
| שיוך | אפס אירועים המשויכים למחקר או לפרומפט שגוי; כל אירוע בעל שיוך חד־משמעי צפוי מקושר אליו |
| כיסוי בריצה תקינה | 100% מההודעות הגלויות ואירועי התצפית שבתסריט ושבתחום האיסוף המתועד נשמרים; אין חוסר שמוסתר בהערת סטטוס |
| כפילויות | אפס מופעים נוספים של אותו אירוע מקור או אותה בקשת ניהול לאחר retry/replay; הודעות זהות אמיתיות נשמרות בנפרד |
| השהיה | אפס תוכן מתקופת ההשהיה במסד ובייצוא המלא, גם לאחר חידוש; מחקר B אינו נפגע מהשהיית A |
| התנגשויות ניהול | בעדכונים מתחרים עם אותה revision אין דריסה אבודה; יש תוצאה שמורה אחת ושגיאת התנגשות מפורשת לשני |
| נפילות יזומות | בכל נקודת כשל המוגדרת בטבלת ההתאוששות מתקבל המצב הצפוי; אין הפעלה אוטומטית חוזרת של פעולת יצירה |
| אי־ודאות באיסוף | פעולה ללא סיום נצפה אינה מוצגת כהצלחה; כשל כתיבה/רענון או מקור לא מאומת אינם מוצגים כאיסוף תקין ומעודכן |
| תאימות להיסטוריה | אימוץ legacy ושדרוג סכמה שומרים את UUID המחקר, מזהי האירועים ותוכנם הקודם; סיווג וייצוא קיימים ממשיכים לעבוד |
| תהליך מלא | שני מחקרים, מקורות וטרמינלים עוברים חיבור, עבודה, החלפת תצוגה, השהיה, חידוש וסיום עם כל התנאים לעיל |

״אפס כפילויות״ מתייחס לזהות אירועי מקור באותו גבול תצפית. אירוע hook חיצוני ואירוע שירות פנימי הם שתי תצפיות מסומנות; אין לספור אותם כהוכחה לפעולה כפולה או כספירה מאוחדת של עבודה בלי התאמה נוספת. במצב שיוך עמום, הצלחה היא השארת prompt ID חסר והצגת אי־הוודאות, ולא ניחוש שיוך.

דרישת 100% כיסוי חלה על הריצה המבוקרת התקינה ועל תחום האיסוף המוצהר. בהזרקת נפילה או באי־זמינות מקור, דרישת המעבר היא התאוששות כשאפשר וחיווי אי־ודאות כשאי אפשר; אין החלפה של אירוע חסר בתוצאה מומצאת. בלי ראיית מקור מספקת מציינים שהשלמות לא אומתה, והתרחיש אינו ראיה לסגירת דרישת הכיסוי.

### ראיות הדרושות לסגירה

נדרש מעבר של בדיקות שירות ו־transport ב־Linux וב־Windows CI, וכן תרחיש קבלה עם לקוח Codex ו־VS Code האמיתיים על Windows. יש לתעד לכל מדד את הצפוי, מה נצפה ותוצאת המעבר. בדיקת API או UI עם mocks בלבד אינה סוגרת את התרחיש האמיתי. כשל באחד המדדים המחייבים נשאר סעיף פתוח גם אם יתר הבדיקות עוברות.

אלה מדדי הצלחה של תשתית ניהול המחקר. השפעה על איכות המצגת, מספר ההתערבויות או זמן העבודה האנושי אינה תנאי הצלחה של פיצ׳ר זה. מדדי הניסוי הללו יוגדרו לאחר איסוף וניתוח 8–10 תהליכי העבודה, כפי שסוכם; עצם שמירת הלוגים אינה מוכיחה שיפור פדגוגי.

הפיצ׳ר אינו כולל סיווג פרומפטים בממשק, מסווג LLM, מדידת זמן אנושי, כלי ניתוח או checkpoints אדפטיביים. הוא אינו כולל עבודת התקנה/אריזה או שינוי תהליך יצירת המצגות. שמירת סיווגים וייצוא קיימים חייבים להמשיך לעבוד, אך מסכי סיווג וייצוא חדשים נמצאים בפיצ׳רים הבאים.

בדיקת ההתקנה והקליטה הידנית ב־Windows Sandbox נשארת משימה פתוחה של פיצ׳ר 1. אפשר לתכנן ולפתח את ניהול המחקרים במקביל, אך אין בכך אישור שסביבת Codex בפועל כבר אומתה. אם בדיקה זו מגלה שינוי בחוזה האירועים, מתקנים את המתאם ומריצים שוב את בדיקות הניהול לפני סגירת פיצ׳ר 2.
