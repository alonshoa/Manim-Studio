# פיצ׳ר 6 — תקינות, התאוששות וייצוא מחקר

תאריך: 31.10.2026. סטטוס: המימוש זמין לבדיקת Windows; [מדריך וחוזה בפועל](../concepts/research-integrity.md), מבוסס על `0bd5529` ובהמשך לפיצ׳רים 4–5.

חוזים משותפים וסדר הבנייה: [תוכנית השלמה](research-completion-plan-he.md).

## מטרה

לפני שימוש במחקר לניתוח, המשתמש יוכל לבדוק אילו נתונים נשמרו, אילו קישורים ותוצרים חסרים, ומה ניתן לשחזר. בלחיצה יוכל לייצא מחקר יחיד עם דוח ואימות תוכן, בלי לחפש ידנית בתוך SQLite ותיקיות builds.

הדוח בודק את הראיות הקיימות. הוא לא יכול להוכיח שלא היו הודעות שמעולם לא הגיעו למתאם, ולא הופך אפס שגיאות checksum להבטחה שכל השיחה נקלטה.

אין איפוס מסד, repair שממציא אירועים, rerun של כלים יוצרים או החזרת קוד לתיקיית העבודה אוטומטית. גם מחקר חלקי ניתן לייצוא, אך החוסרים נשארים בתוכו.

## בסיס קיים

כבר קיימים קבלות retry, CAS של lifecycle וסיווג, capture gaps ופעולות start ללא finish. הייצוא הנוכחי הוא JSONL לכל הפרויקט עם אופציית תוכן. הפיצ׳ר יאחד בדיקות והתאוששות, יוסיף job עמיד וייצוא scoped, וירחיב את ה־metadata allowlist לשדות החדשים. הוא אינו ״בונה התאוששות מאפס״.

## מסך פרטי מחקר

פקודה `manimStudio.research.showIntegrity` פותחת את המחקר הנבחר, עם כפתורי ״בדיקה״, ״בדיקת תוכן מלאה״, ״התאוששות״ ו־״ייצוא״.

| תחום מוצג | דוגמאות |
| --- | --- |
| שיחה | מקור מחובר, גבול כיסוי, פערים ידועים, סטטוס delivery לא מאומת |
| קישורים | prompt/parent/action/proposal שאינם שייכים למחקר או חסרים |
| החלטות וגרסאות | intent ללא outcome, מועמד חסר, retained עם hash לא תקין |
| תוצרים | pending/missing/purged/omitted; הסיבה ומדיניות השימור שהייתה בתוקף |
| זמן ומטא־דאטה | timer interrupted, חפיפות, provenance חסר, מודל לא ידוע |
| אחסון | סכמת מסד, jobs שנקטעו, קבלות לא עקביות, שגיאת קריאה/כתיבה |

כל finding כולל code יציב, severity, ישות/אירועים קשורים, הסבר קצר ופעולות אפשריות. הודעות שגיאה אינן מכילות prompt/source text כברירת מחדל. אין סטטוס ירוק שמעלים partial/unverified.

מצב כל תחום הוא valid, partial, unverified או invalid. findings מוגדרים בנפרד כ־error/warning/info. הדוח כולל snapshot sequence, גרסת checker וזמן סיום; דוח ישן נשאר מזוהה כישן כאשר מגיעים אירועים חדשים.

## חוזה בדיקת השלמות

הבדיקה נצמדת ל־read snapshot ב־SQLite. `snapshot_seq` הוא גבול עליון גלובלי; רצף ה־seq של מחקר אחד לא חייב להיות רציף כי מחקרים אחרים כותבים באותו מסד.

| בדיקה | כלל |
| --- | --- |
| זהות | כל entity/event ref קיים באותו project/research; קישורים מותרים לפרויקט מוגדרים במפורש |
| פעולות | לכל finish יש start תואם; start פתוח במהלך פעולה חיה הוא pending, לא כשל מידי |
| capture | gaps, גבולות pause, duplicates מדווחים וכשלי adapter; null prompt מותר ואינו שגיאה כשלא ידוע |
| סיווג | replay עם הטקסונומיה ההיסטורית, ה־human head הנכון והפרדת הצעת מודל |
| מסמכים | manifest תקין, hashes קיימים, omission/delete מפורשים, אין path מחוץ להיקף |
| החלטות | אותו candidate hash מופיע בבקשה ובתוצאה; failed אינו accepted; מקור unknown גלוי |
| שימור | retained reference מצביע לתוכן מאומת; pending אינו retained; purged אינו מוצג כהשחתה לא מוסברת |
| זמן | intervals תקפים, checkpoint sequence ללא כפל, חפיפות ואנומליות שעון לפי פיצ׳ר 5 |
| גרסאות | migration נתמך, run contexts מפורשים, fields חדשים אינם מיוחסים אוטומטית לאירועים ישנים |

בדיקה מהירה קוראת מבנים, manifests ומידע אחסון. בדיקה עמוקה קוראת את כל ה־bytes הנדרשים ומחשבת SHA-256 מחדש. ״בדיקה מהירה עברה״ אינו ״כל קובצי הווידאו אומתו״. שניהם jobs ברקע הניתנים לביטול, עם התקדמות ותקציב זיכרון; אין קריאת כל וידאו ל־RAM.

תוצאה תבחין בין ״עקביות פנימית תקינה״, ״יש פערים ידועים״ ו־״מסירת המקור לא אומתה״. סגירת פער דורשת ראיה או acknowledgment מסומן, ואישור שהמשתמש ראה אזהרה אינו הופך פער לנתון שנאסף.

## התאוששות — מה מותר לעשות

| מצב | פעולה מותרת | מה אסור להסיק |
| --- | --- | --- |
| תשובת mutation אבדה | retry עם request ID והפרמטרים המקוריים | אין ליצור request חדש במקום אותו ניסיון |
| start בלי finish אחרי קריסה | לבדוק receipts/manifests/מצב יצירה סמכותי; append של reconciliation עם evidence | אין לשחזר outcome לפי שם הקובץ או להריץ שוב accept/render |
| artifact job נקטע | לאמת staging/תוכן סופי ולחדש העתקה מאותו מקור מקובע | אין לקרוא קובץ חי חדש כאילו היה הגרסה הישנה |
| טיימר נקטע | לסגור לפי checkpoint מאושר ולשמר uncertainty | אין להוסיף זמן מאז ה־heartbeat האחרון |
| DB locked/disk full | שגיאה מפורשת, שמירת pending מקומית, retry לאחר תיקון הסיבה | אין חיווי ״נשמר״ |
| blob חסר או פגום | לחפש עותק בעל hash זהה בארכיון/גיבוי מאושר; לתעד recovery | אין להחליף בקובץ דומה בעל hash אחר |
| אירוע source לא הגיע | להציג coverage gap וראיות זמינות | אין backfill אוטומטי של שיחה מתקופת pause |
| מסד לא תקין | גיבוי/שחזור לקובץ חדש בהליך מפורש ובדיקתו | אין דריסה או ״תיקון״ אוטומטי של המקור |

reconciliation מסמן את האירוע והראיה שמבססים אותו; האירוע הישן נשאר. אם אין ראיה מספקת, outcome נשאר unknown. סטטוס הפעולה המחקרית אינו מנגנון ל־exactly-once של פעולת יצירה חיצונית.

אפשר להפיק גיבוי מסד באמצעות SQLite backup API, גם לצורך migrations. העתקת `events.sqlite3` בלבד בזמן כתיבה אינה חוזה גיבוי. שחזור לא יוחל על מסד פתוח ולא יחליף מחקר חדש שכבר נוצר מאז הגיבוי. הוראות ו־UI ישמרו את המקור וידרשו בחירת יעד חדש.

## ייצוא scoped ואטומי

מתוך המחקר בוחרים:

1. **מטא־דאטה**: אירועים מסוננים, IDs, hashes, קטגוריות, זמנים, provenance, היקף וחוסרים. ללא prompt/response/source/log bytes, arguments/results או טקסטי other/feedback חופשיים.
2. **תוכן מלא שנשמר**: כל הנ״ל, תוכן האירועים ו־bytes שזמינים בארכיון עד גבול הייצוא. omitted/purged נשארים חסרים ומוצהרים.

מטא־דאטה אינו אנונימיזציה: מזהים, נתיבים יחסיים ופרטי גרסה עשויים לחשוף הקשר. סינון יהיה לפי סוג אירוע עם allowlist לשדות מקוננים; ה־allowlist השטוח הישן אינו מספיק לחוזים החדשים. run contexts מוחרגים מ־secrets, וה־raw transcript החיצוני אינו מצורף אוטומטית.

הפורמט החדש הוא ZIP עם `manifest.json`, `events.jsonl`, `integrity.json`, `summaries/time.json` ו־content-addressed entries לפי הצורך. manifest כולל export ID, project/research IDs, mode, schema/export/checker/aggregation versions, snapshot sequence, hashes וגדלים של כל member. manifest אינו מכיל hash של עצמו.

ייצוא מחקר אחד כולל רק אירועים שלו וה־blobs/context/policy records שאליהם הם מפנים. תוכן שמשותף לשני מחקרים נכלל פעם אחת אם המחקר הנבחר זקוק לו; אין לכלול אירועים או תוכן לא נדרש של המחקר השני. אירועי פרויקט משותפים יצורפו רק ב־dependency section מוגדר, עם reason, ולא כייבוא גורף של המסד.

## רצף job והבטחת עקביות

1. `exports.start` מאמת scope, מצב, יעד ו־request ID; שומר job וקבלה. אין צורך לסיים או להשהות את המחקר.
2. worker מקבע snapshot של האירועים, projections ותלויות התוכן. תוכן immutable שנדרש מקבל pin נגד purge עד סיום/ביטול ה־job; רשימת refs והגבול נשמרים עמידים. אם אי אפשר לחדש אותה תמונת מצב אחרי קריסה, ה־job נכשל ומציע יצירת ייצוא חדש, ולא ממשיך עם נתונים חדשים בשקט.
3. בדיקה עמוקה של התוכן שנכלל ויצירת דוח המתייחס בדיוק לאותה תמונה. findings, חוסרים וביטולים אינם מסוננים כדי לגרום להצלחה.
4. כתיבה בזרימה לקובץ staging ייחודי באותה תיקיית יעד, עם בדיקות hash תוך כדי. הנתיב נבחר בצד ה־host; אין כתיבה על DB, artifact store או source tracked של הפרויקט.
5. סגירת הארכיון, flush ואימות, ואז פרסום אטומי ללא overwrite. אם filesystem אינו תומך בחוזה פרסום זה, מוחזרת שגיאה ולא ״הצלחה משוערת״. קיים יעד באותו שם: `destination_exists`.
6. receipt סופי שומר path, hash של הארכיון ומצב completed. אם יש קריסה לאחר פרסום ולפני receipt, retry בודק export ID ו־hash של הקובץ הסופי ומאמץ אותו רק אם הוא אותו job. קובץ זר לא נדרס.

קובץ חלקי לא מוצג כייצוא תקין. cancel משחרר pins ומנקה רק staging ששייך ל־job; retry של completed אינו יוצר ארכיון נוסף. יש להציג התקדמות ולהשאיר את ממשק היצירה ואת פעולות הטיימר זמינים בזמן בדיקה/דחיסה.

אירועים חדשים תוך כדי ייצוא אינם נכנסים אליו; לאחר סיום מוצגת האפשרות לייצוא נוסף עם גבול חדש. מחקר ללא פרומפטים ניתן לייצוא אבל אינו מסומן כניסוי מלא. ייצוא legacy JSONL נשאר זמין ותואם; ה־UI החדש משתמש בחבילת הייצוא הייעודית.

## אימות עצמאי ושחזור

תתווסף פקודת `studio research verify-export PATH` שמוודאת schema, member inventory, hashes וקישורים בלי גישה לפרויקט המקורי. ארכיון עם paths מוחלטים, `..`, duplicates, symlink entries או גדלים שחורגים מהמוצהר נדחה; אין חילוץ בלתי מוגבל או ביצוע קוד מהארכיון.

שחזור לצורכי בדיקה יוצא לתיקייה חדשה בלבד. replay של סיווגים, snapshots, החלטות וזמנים מפיק את אותו מצב בגבול הייצוא. יכולת לשחזר source bytes אינה מבטיחה render זהה על חומרה או חבילות שונות; metadata ישקף זאת. metadata-only אינו אמור לאפשר שחזור תוכן, והבודק יציין שזה mode תקין ולא חוסר מקרי.

## API, migrations ובדיקות

RPC מוצע: `integrity.check/status/findings/reconcile`, `exports.start/status/cancel/list`. פעולות כתיבה כוללות request ID והגנת גרסה לפי הישות. בקשת reconcile מכילה evidence refs ולא פקודת shell. פקודות CLI/MCP משתמשות באותם שירותים. transport jobs נפרד מתור הסיווג/טיימר ומהתור הסינכרוני של היצירה.

schema v7 מוסיף jobs, pinned refs ונתוני דוחות באמצעות runner שנבנה בפיצ׳ר 4. migration transaction נכשלת משאירה את הגרסה הקודמת; DB עתידי או read-only מקבלים שגיאה מובנית. exports הם פורמט בעל version משלו שאינו חייב להשתנות בכל שינוי סכמת SQLite.

| בדיקה | תנאי מעבר |
| --- | --- |
| דוח על fixtures תקינים/פגומים | כל finding הצפוי ורק הוא, כולל null לגיטימי, global seq gaps ו־legacy |
| checksum וכיסוי | קובץ שהושחת/נמחק מזוהה; coverage unknown אינו ״תקין מלא״ |
| שני מחקרים | ייצוא אחד מכיל אפס תוכן לא נדרש של השני, גם עם dedup פיזי משותף |
| כתיבה בזמן ייצוא | כל החבילה והדוח משקפים אותו cutoff; אין שילוב תיקון חדש עם ראש ישן |
| נפילה לפני/אחרי פרסום | אין קובץ סופי חלקי; retry מזהה בדיוק את אותה תוצאה, ללא דריסת יעד |
| purge מול export | תוכן נדרש pinned; cancel/finish משחררים pins בלי לפגוע במחקר אחר |
| metadata-only | בדיקת sentinel בטקסטים ובשדות מקוננים מוכיחה שאין דליפת content/free text/secrets |
| ZIP פגום/זדוני | checksum/path/size validation נכשל לפני חילוץ; אין כתיבה מחוץ ליעד |
| recovery ו־migration | אין המצאת outcome או replay של יצירה; כשל שדרוג אינו משאיר חצי schema |
| Windows UI | בחירת מחקר ויעד, בדיקה, ביטול וייצוא בלי JSON; עבודה ותיוג ממשיכים במקביל |
| רצף ניסוי משותף | התסריט שבמסמך הראשי עובר מול השיחה והפעולות בפועל, לא רק מול ה־ledger |

סדר מימוש: checker ודוח → recovery בטוח → scoped export planner/סינון → worker/אטומיות/pins → verifier עצמאי → ממשק → הזרקות כשל ובדיקת Windows מקצה לקצה. אין לסמן את פיצ׳ר 6 כסגור לפני שהחבילה נבדקה ללא המסד וה־builds המקוריים.
