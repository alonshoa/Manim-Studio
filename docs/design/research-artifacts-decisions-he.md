# פיצ׳ר 4 — כיסוי קבצים, תוצרים והחלטות

תאריך: 31.10.2026. סטטוס: מומש ונבדק מקומית על בסיס `0bd5529`; [מדריך ותוצאות](../concepts/research-artifacts.md). קבלה בתוך VS Code ב־Windows נשארת פתוחה.

חוזי הזהות, השדרוג, ההרשאות המקומיות והבדיקות המשותפות: [תוכנית השלמה](research-completion-plan-he.md).

## מטרה וגבולות

לאפשר לענות על השאלה: ״מה בדיוק הוצע והוצג, איזו החלטה ניתנה, ומה היה מצב התוכן לפניה ואחריה?״ גם אחרי שהצעה נדחתה, קובץ שונה או תיקיית build נמחקה.

דוגמה: במחקר על וקטורים נשמרים מערך שיעור, storyboard, קוד מועמד וקטע וידאו. המשתמש דוחה את ההצעה בגלל סדר ההסבר. המחקר שומר את ההצעה שנדחתה ואת החלטתו; התיקון והאישור הם רשומות נוספות ולא החלפה שלה.

זהו ארכיון ראיות מוגדר בהיקפו, לא גיבוי כל המחשב, מערכת Git חלופית, מעקב הקלדות או מדד לאיכות פדגוגית. ״הוצג״ פירושו שהממשק דיווח שפתח תוצר מסוים; אין בכך הוכחה שהאדם צפה בכולו.

## תשתית קיימת וחיבור לקוד

`ResearchLog.snapshot` שומר היום `catalog/scenes.yaml` וקובצי Python/JSON מתוך scenes, decks ותיקיית authoring. גבולותיו הנוכחיים: מיליון bytes לקובץ ועשרה מיליון ל־snapshot. הוא אינו כולל באופן כללי מערכי שיעור, Markdown ו־YAML אחרים.

אירועי `action.started/finished` כבר מפנים לתמונות מצב. staged proposals ו־build manifests קיימים במערכת היצירה. יש להרחיב את השימור סביב המעברים ב־`authoring_sessions`, `staged_edits` ו־`movie_sessions`, ולא להסיק החלטה אנושית מהשם של wrapper ב־MCP. CLI, MCP ו־RPC שמשתמשים באותו מעבר יקבלו אותו hook; wrappers מקוננים יעבירו transition ID כדי לא ליצור החלטות כפולות.

## בחירת היקף ומדיניות שימור

הגדרות איסוף מפורשות ברמת פרויקט, עם override למחקר והיסטוריית revisions. בעת התחלה מוצג ההיקף האפקטיבי; שינוי חל רק קדימה ונרשם באירוע. הגדרה חדשה אינה מפעילה capture שהיה כבוי.

| רכיב | ברירת מחדל מוצעת |
| --- | --- |
| מקורות קיימים | נשמרים לפי ההיקף הקיים |
| מסמכי תהליך | `lesson-plan*.md`, `storyboard*.md` בשורש; MD/YAML/YML תחת `research-inputs/` שהמשתמש בחר להשתמש בה |
| הרחבת היקף | בחירת קבצים/תיקיות יחסית לפרויקט ומסיומות מותרות; preview של הרשימה לפני אישור |
| החרגות קשיחות | `.git`, `.venv`, `venv`, `node_modules`, תיקיית ledger, קובצי credentials ו־`.env`; אין סריקה כללית של תיקיית המשתמש |
| תקציב מסמכים | 1 MB לקובץ, 10 MB ו־500 קבצים ל־snapshot; ייחשבו לפי bytes שנקראו בפועל |
| ראיות build | manifest, קוד מועמד וקוד מקור קשור; וידאו preview/תוצר סופי עד 100 MiB לקובץ; לוג עד 5 MiB |
| מכסה | 2 GiB למחקר ו־10 GiB לפרויקט לתוכן הנשמר, ניתנים להגדלה מפורשת; תוכן משותף לא נשמר פעמיים בדיסק |
| חריגה | metadata נשמר, bytes אינם נשמרים ומסומנים `omitted_quota/too_large`; אין קיצוץ שקט או מחיקה אוטומטית של ראיות קודמות |
| מחיקה | אין TTL אוטומטי בתקופת הניסוי. מחיקה יזומה מציגה מה ייאבד ונרשמת כ־`artifact.purged`; המחיקה הפיזית מותרת רק כשאין reference חי אחר |

אי אפשר להבטיח שימור מלא עם מכסה סופית. ״מלא״ מוגבל למדיניות האפקטיבית ולתקציב; חריגות יוצגו במסך ובייצוא. כל path מיוצא נחשב מידע שעשוי לחשוף הקשר גם ללא תוכן.

## מודל הנתונים

`snapshot_id` מתאר תצפית קבצים בנקודה מסוימת. manifest מכיל path יחסי, סוג, גודל, SHA-256 ומצב לכל קובץ; גם היעדר קובץ שהיה ב־snapshot קודם מתועד. SHA זהה אינו מבטל snapshot חדש בזמן אחר.

`artifact_id` הוא זהות תוצר שנצפה: role כגון candidate_source, preview_video, render_log, build_manifest או planning_document; קישור מפורש ל־snapshot/proposal/build/authoring session; prompt יכול להיות null. candidate revision נבחר לפי hash של ה־bytes ולא לפי שם proposal בלבד.

`decision_id` מייצג ניסיון מעבר אחד: accept, reject או request_revision. שדותיו כוללים proposal ID, candidate hash, baseline hash, מקור, client/action/request IDs, timestamps, status ו־before/after snapshot IDs. intent וכשל ביצוע אינם החלטה שבוצעה. אישור שנכשל ברינדור אינו מוצג כגרסה שהתקבלה.

| אירוע חדש מתוכנן | משמעות |
| --- | --- |
| `snapshot.recorded` | manifest של תצפית, מדיניות וחריגות |
| `artifact.observed` | ידוע שתוצר מסוים קיים, גם אם עדיין לא הועתק |
| `artifact.retained` / `artifact.unavailable` | ראיה נשמרה ואומתה, או סיבה מפורשת לחסר |
| `artifact.presented` | client דיווח פתיחת hash מסוים; preview שנוצר בלבד אינו ״נצפה״ |
| `decision.requested` | בקשת מעבר עם המועמד והמקור המוצהר |
| `decision.completed` / `decision.failed` | תוצאת המעבר המאומתת; כשל אינו מוחק בקשה |
| `coverage.observed` | אי־התאמה/עריכה שנצפתה ללא שיוך; לא ממציאים לה כותב |
| `artifact.purged` | ויתור מפורש על תוכן שנשמר, ללא מחיקת האירועים |

projections/indexes במסד יאיצו רשימות וחיפוש. מסמכי מקור קטנים יכולים להמשיך להשתמש בטבלת blobs; תוצרים גדולים יישמרו תחת `.manim-studio/research/artifacts/sha256/...`. API הקריאה יחזיר storage reference מאומת, לא path חופשי שה־webview בחר.

## מקור ההחלטה

`decision_origin = human | automation | unknown` נפרד מ־actor הקיים. UI מפורש מעביר human בצירוף client ופעולת משתמש; פעולה שיזם מודל/כלל מעבירה automation. legacy או caller ללא מקור מזוהה נשאר unknown. ערך actor=system אינו מספיק לסיווג המקור, ו־`confirm='accept'` אינו ראיה לאדם.

ה־API המקומי אינו מאמת פסיכולוגית או קריפטוגרפית שמי ששלח human היה אדם. יש לשמר גם `origin_evidence` ו־`reported_by`, ולהציג שזה מקור מדווח. לא מסווגים אוטומציה כאנושית בגלל שקדמה לה הודעת משתמש.

## רצף שימור והחלטה

1. פותרים ומאמתים project/research/proposal/candidate/epoch מתוך ההקשר המפורש. אם אין מחקר ידוע, היצירה ממשיכה ללא שיוך מדומה.
2. לפני accept/reject/revise מקבעים את קוד המועמד וה־baseline שהמעבר עומד להשתמש בהם, בגבולות snapshot. מחשבים hash ובודקים שהגרסה לא התחלפה לפני הביצוע.
3. רושמים בקשת החלטה; מפעילים את מעבר היצירה הקיים פעם אחת. לא הופכים את מחקר ה־SQLite ואת שינוי קובצי היצירה לטרנזקציה גלובלית מדומה.
4. מסמנים completed רק לאחר שמצב היצירה/קבלת המעבר הקיימת מאשרים תוצאה, ורושמים את הגרסה שלאחר המעבר. נפילה בין השלבים משאירה outcome_unknown עד reconciliation בפיצ׳ר 6.
5. תוצרי build גדולים מוכנסים לתור עמיד. מקור התור חייב להיות קובץ build בלתי משתנה עם hash צפוי או עותק מקובע; path שעתיד להידרס אינו מספיק. אין להצהיר retained לפני אימות bytes בארכיון.

שירות השימור כותב לקובץ staging, מאמת hash/גודל, מפרסם בשם תוכן אטומי ורק אז מחבר reference במסד. נפילה לפני reference יכולה להשאיר orphan לבדיקה; נפילה אחרי reference אינה אמורה ליצור retained שמצביע לקובץ שטרם פורסם. אימות checksum מאוחר יכול עדיין לחשוף מחיקה/השחתה.

מועמד קצר נשמר לפני מעבר שעלול לאבד אותו; העתקת וידאו אינה חוסמת accept/reject או שליחת פרומפט. תור מלא או כשל אחסון מייצרים gap/warning ו־unavailable, בלי לשנות את התוצאה המקורית. אם גם הדיאגנוסטיקה אינה נכתבת, האזהרה זמינה ב־Output והסטטוס אינו ״שלם״ אחרי הבדיקה הבאה; אין הבטחת תיעוד באפס מקום בדיסק.

## היקף התצפית, השהיה ועבודה מקבילה

snapshots יתבצעו בתחילת מחקר, לפני/אחרי מעברים נתמכים ובנקודת checkpoint מפורשת. חיווי filesystem בתוסף יכול לבקש snapshot מאוחד בזמן capture פעיל, אך אינו ראיה למי ערך או למה. אין snapshot על כל הקלדה.

בלי התוסף או hook מתאים, שינוי ישיר יתגלה רק בהשוואה לנקודת התצפית הבאה; שינוי שנוצר ונמחק בין שתי תצפיות יכול לא להיקלט. CLI לא מתועד ותהליכים חיצוניים יופיעו כהיקף לא מאומת, לא כפעולות שלא התרחשו. מחיקת קובץ תזוהה רק ביחס ל־baseline ידוע.

עם pause/finish נעצרת קליטת תוכן חדשה. bytes שקובעו קודם רשאים לסיים העתקה; worker אינו קורא מצב חי מתקופת ההשהיה. snapshot אחרי resume מתאר מצב נוכחי, ולא מוכיח שהעריכות נוצרו בתקופה הפעילה. baseline שנאסף אחרי pause יסומן עם boundary caveat.

לשני מחקרים יש קישורים ומונים נפרדים, גם אם bytes משותפים באחסון. שני כותבים לאותה הצעה מחייבים version check במעבר היצירה; תיעוד אינו מנגנון מיזוג. שינויים משותפים לאותו פרויקט בזמן מקביל מוצגים עם שיוך לא ודאי לפי הצורך.

## אבטחת קבצים וממשק

רק קבצים תחת root מאושר וב־allowlist ייקראו. אין לעקוב אחרי symlink, junction/reparse point או path מחוץ לפרויקט. צריך לאמת את קובץ ה־handle בפועל מול race בזמן פתיחה ולכבד מגבלות תוך כדי קריאה, כולל קובץ שגדל. manifest זדוני של build אינו מוסיף הרשאת קריאה.

מסך ״תוצרים והחלטות״ כולל timeline, מקור החלטה, השוואת before/after, hash/גרסה, מצב pending/retained/missing/purged, וקישור לקריאה מתוך העותק השמור. אין כפתור restore שמחליף קוד עבודה בגרסה הראשונה. קוד מוצג כטקסט ו־CSP נשמר; קובץ ייפתח רק אחרי בדיקת storage reference בצד ה־host.

פקודות מוצעות: `manimStudio.research.showArtifacts`, `captureCheckpoint`, `configureCaptureScope`. RPC מוצע: `artifacts.list/get/history/checkpoint/configure/purge/job_status`. configure/purge דורשים expected revision ו־request ID; checkpoint חוזר עם אותו ID לא יוצר שתי תצפיות.

## בדיקות ותנאי סגירה

| בדיקה | תוצאה נדרשת |
| --- | --- |
| Markdown/YAML ושינוי/מחיקה | bytes/hash והבדלים זהים ל־fixtures; קובץ שנמחק נשאר זמין מהתצפית הקודמת |
| accept/reject/revise | המועמד המדויק נשמר לפני המעבר; מקור חסר נשאר unknown; render failure אינו accepted |
| שינוי מועמד במקביל | אין החלטה שמוצגת בטעות כמתייחסת לגרסה אחרת; conflict או outcome מפורש |
| CLI/MCP/RPC ו־wrappers מקוננים | אותו transition מקבל החלטה אחת, קישור נכון ואפס המצאת prompt |
| ניקוי builds | תוצר במצב retained עדיין נפתח מארכיון המחקר לאחר מחיקת build המקור |
| quota/lock/disk failure | חריגה מפורשת; התוצאה המקורית של פעולת היצירה נשמרת; אין retained פיקטיבי |
| קריסה בשלבי פרסום | אין reference תקין לקובץ חצי כתוב; orphan ניתן לזיהוי; unknown אינו מורץ שוב |
| symlink/junction/race/קובץ גדל | אפס קריאות מחוץ להיקף, אפס חריגות מגבולות הקריאה שהוגדרו |
| השהיה ושני מחקרים | אין backfill של תצפיות מההשהיה או ערבוב קישורים; caveats נשמרים |
| UI ב־Windows | אפשר לראות גרסה שנדחתה, תוצר חסר ומקור החלטה בלי JSON; יצירה נמשכת בזמן העתקה |

סדר מימוש: סכמות ומדיניות → שירות snapshot/ארכיון → hooks במעברים וב־builds → תור והתאוששות בסיסית → מסך ו־API → בדיקות שירות/transport/Windows וקבלה. יכולת בדיקת hashes בסיסית נדרשת כאן; הדוח המאוחד והייצוא מגיעים בפיצ׳ר 6.
